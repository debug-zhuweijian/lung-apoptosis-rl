# YAML 调参说明与八条件合批

日期：2026-09-28。适用于当前 `I:/科研/肺癌细胞凋亡-强化学习` 的代码。

## 这次已经修改什么

默认响应计算合批改为 8。后续按用户要求取消预取对更新组条件数的固定上限；当前用户配置为每 16 个条件更新一次、每批计算 8 个条件。默认开启单线程、最多一个待取组的 CPU 数据预取，以及主线程固定内存缓冲区和非阻塞 GPU 传输。GPU 网络计算各条件合批，OT 与 MMD 仍按条件分别计算；末尾不足一批的条件按实际数量处理。时间分支的相同紧凑骨干路径也接入合批。

八条件合批和下一组预取作用于训练更新。当前独立验证仍沿用原来的逐条件评价流程；恢复时先出现第 9 轮验证属于预期行为，不能用该段利用率代表八条件训练的速度。

预取仅对 `compact_full_gene + observed + full + direct` 路径启用；其他结构或训练阶段保留串行路径。工作线程只抽取 CPU 数据，使用私有 NumPy 随机流；消费该组后才提交主随机状态，验证前等待后台读取结束。当前没有新增独立 CUDA stream，所以不能把 `non_blocking` 说成已经实现传输和 GPU kernel 的跨流重叠。

条件元数据缓存从 8 个条目改为最多 128 个条目、64 MiB 估算容量，仍按 role 和 condition 隔离。原始数据、全基因范围、每条件样本数、ODE 步数、五成员以及 DA-AC/DLPA 两条路线不变。

首次八条件合批修改按用户要求未运行测试、训练、基准或显存压力检查，仅完成源码静态审查、语法解析、配置读取及检查点完整性核对。八条件是否能在这张 10 GiB 显卡的所有阶段放下、是否提速、浮点结果差异，尚未运行验证；不会自动从 8 降到 4，也不声称共享内存能够避免 CUDA OOM。

Windows 的共享 GPU 内存来自普通系统内存，不能把 10 GiB 专用和约 16 GiB 共享当作同等速度的 26 GiB 板载显存。[Microsoft 对专用与共享内存的定义](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)

## 1. 先认识配置文件

| 文件 | 管什么 |
| --- | --- |
| `configs/train.yaml` | 总流程、轮数上限、设备、早停、验证和保存频率、界面 |
| `configs/response.yaml` | 药物响应模型、条件合批、样本数、学习率、生成步数 |
| `configs/daac.yaml` | DA-AC 的回合、经验池、Actor/Critic 更新 |
| `configs/dlpa.yaml` | DLPA 的候选搜索、精英数和提案学习 |
| `configs/dataset.yaml` | 冻结数据版本、划分和资产路径；不作为日常加速旋钮 |
| `configs/timecourse.yaml` 等 | 时间分支专用设置；可能覆盖公共响应设置 |

默认入口加载 `train.yaml`，再合并 `response.yaml`、`daac.yaml`、`dlpa.yaml`。如果 `train.yaml` 自己写了同名嵌套字段，以 `train.yaml` 的该字段为准。例如下方覆盖的是响应配置中的合批宽度：

```yaml
# 在 train.yaml 中的写法，注意 response 下有两格缩进。
response:
  condition_microbatch: 4
```

直接编辑 `response.yaml` 时对应参数在文件顶层，不再包一层 `response:`。避免在多个文件重复覆盖同一参数，否则容易出现“我改了却没生效”。

## 2. YAML 的基本写法

```yaml
epochs: 1000             # 整数；井号后面是说明，不参与运行
device: cuda:0          # 第一张 GPU
progress: true          # 布尔开关，不要写成字符串 "true"

early_stopping:
  enabled: true         # 用空格缩进，不用 Tab
  patience: 20
  min_delta: 0.0001
  min_updates: 1000
```

键名和冒号后面留一个空格；同一级参数对齐；不要写中文冒号。整数不要带“次”“GB”等单位，除非该字段本来要求字符串。小数优先直接写 `0.0001`；路径建议用正斜杠，如 `I:/科研/肺癌细胞凋亡-强化学习`。不要重复写两个同名键，也不要自行拼写未实现的新字段。

以下示例都是局部片段，只改对应行，不能拿片段覆盖整个配置文件。

## 3. 先学这几个速度和显存参数

本轮 `configs/response.yaml`：

```yaml
conditions_per_update: 16
condition_microbatch: 8
prefetch_group: true
pin_memory: true

cfm_samples: 128
mmd_samples: 32
microbatch: 128
mmd_microbatch: 32
inference_microbatch: 128
```

| 参数 | 含义 | 调整时的影响 |
| --- | --- | --- |
| `condition_microbatch` | 同时送进网络的条件数；当前支持 1、2、4、8 | 优先用于调整计算合批和显存。不是越大越快，默认当前为 8；部分不兼容路径仍串行 |
| `conditions_per_update` | 累计多少个条件后执行一次优化器更新 | 正整数，当前用户设为 16；改变有效批量和更新次数，不是纯显存开关 |
| `prefetch_group` | GPU 计算当前组时，后台准备下一组 CPU 数据 | 不再限制每组最多 8 个条件；始终最多预取一组，组越大占用的系统内存越多 |
| `pin_memory` | 通过固定内存缓冲区上传响应批次 | 可能改善传输，也有固定内存分配代价；实际收益未测 |
| `microbatch` | 一个条件的 CFM 样本分块宽度 | 当前逻辑样本数只有 128，再把它改成 256 不会凭空多算 256 个样本 |
| `mmd_microbatch` | 一个条件在生成 MMD 群体时的分块宽度 | 当前逻辑 MMD 群体为 32；直接反传仍保留完整 ODE 图，减小它不保证大幅降低全部激活峰值 |
| `inference_microbatch` | 推理分块大小 | 影响验证/推理阶段显存及调用次数；不是训练条件合批宽度 |

理解两个条件批量参数：

```text
以 conditions_per_update=8 为例：
condition_microbatch=2：2+2+2+2 后更新一次参数
condition_microbatch=4：4+4 后更新一次参数
condition_microbatch=8：8 个合批后更新一次参数

当前 conditions_per_update=16、condition_microbatch=8：
8+8 后更新一次参数，prefetch_group 可以保持 true。
```

末尾仅剩 4 个条件时更新组就是 4，不伪造额外数据。各条件自己的 MMD 群体保持分开。

若今后发生显存不足，可以把新的实验配置的 `condition_microbatch` 从 8 改为 4 或 2。当前正在保留的续训配置已经按 8 登记；修改后可能选中新的实验，不能认为改数值就会无条件继承旧检查点，见第 7 节。

`num_workers` 当前必须为 0，本项目的单线程预取由 `prefetch_group` 控制；不要把它随手改成 8。

## 4. 控制训练轮数、验证和早停

这些参数位于 `configs/train.yaml`：

| 参数 | 当前值 | 应怎样理解 |
| --- | ---: | --- |
| `epochs` | 1000 | 各训练阶段的轮数上限，不是整套 19 项任务加起来总共 1000 轮 |
| `early_stopping.enabled` | true | 仅有合法选择数据的模块按验证结果早停；不能用测试集或训练回报替代 |
| `early_stopping.patience` | 20 | 连续多少次验证没有足够改善后允许停止，不一定等于 20 个 epoch |
| `early_stopping.min_delta` | 0.0001 | 小于最佳损失至少这么多才算改善；需要结合指标尺度理解 |
| `early_stopping.min_updates` | 1000 | 允许早停前的最少优化器更新次数，不是最少 epoch |
| `training_control.validation_every_epochs` | 1 | 每轮检查验证是否到期；最终完成仍有相应验证要求 |
| `training_control.checkpoint_every_seconds` | 60 | 经过此时间后，在完整更新边界保存；不是从计算中途截断 |
| `training_control.checkpoint_every_updates` | 0 | 不额外按固定更新次数触发保存；时间触发仍开启 |

如果同时开启按时间和按更新次数保存，满足任一条件就可能保存，关键边界还会强制保存。两种触发不能同时禁用。

把验证间隔从 1 改到 5 会减少验证次数，但也会改变模型选择时机和早停速度，不是无影响的加速开关。同样，把 `patience` 从 20 改到 10 可能更早停止，也可能错过后续改善；本轮没有替你修改这些设置。

当前 A549 响应阶段一轮是 644 次条件抽样，有放回、按来源和条件组织；不是遍历全部细胞，也不保证每个条件恰好出现一次。每次再抽取其 CFM/MMD 细胞群体。DA-AC、DLPA 中的 epoch 含义见下节。

## 5. 学习率和强化学习参数

响应学习率在 `response.yaml`：`lr: 0.0001`，`min_lr: 0.00001`，`warmup_epochs: 10`。学习率影响参数更新幅度，不能当作硬件利用率旋钮。修改学习率、预热、模型宽度或层数时，应建立明确的新实验，不把它称为原训练的等价继续。

| 文件与参数 | 当前值 | 含义 |
| --- | ---: | --- |
| `daac.yaml / episodes_per_epoch` | 128 | 每轮训练收集的回合数 |
| `daac.yaml / batch_size` | 256 | 从经验池抽取的训练批量，与响应模型的条件合批不同 |
| `daac.yaml / actor_lr` | 0.0001 | 策略网络学习率 |
| `daac.yaml / critic_lr` | 0.0003 | 价值网络学习率 |
| `dlpa.yaml / roots_per_epoch` | 64 | 每轮用于规划/训练的根状态次数 |
| `dlpa.yaml / candidates` | 256 | 一轮规划搜索的候选数量 |
| `dlpa.yaml / iterations` | 6 | 规划搜索的迭代次数 |
| `dlpa.yaml / elites` | 64 | 保留用于更新提案的精英数量，不应大于候选数 |
| `dlpa.yaml / distill_updates` | 200 | 每轮提案学习更新次数 |

增加这些数值会增加计算量，也会改变搜索或学习过程，收益没有单调保证。它们与当前正在训练的响应模型属于后续阶段；现在调 DA-AC 的 `batch_size` 不会改变眼前响应模型的显存。

## 6. 暂时不要随手改的内容

- `cfm_samples`、`mmd_samples`、`ot_samples`：改变估计使用的样本数。
- `train_ode_steps`、`inference_ode_steps`：改变积分近似，涉及数值精度和审计。
- `members`、`model.n_genes`、模型骨干/宽度/层数：改变模型或集成；主数据合同固定全 32,461 基因。
- 数据划分、标准化资产、奖励定义、随机种子：影响实验含义或复现。
- 默认完整流程中的 `workflow`、`task`、`algorithm`：当前完整套件要求 `research_all / PROXY-A549-V1 / both`，不能只改成 `algorithm: daac` 就期待继续执行原 19 项图。

这些都可以成为正式研究的调参或消融，但需要明确比较目的，不能为了让进度更快就和原实验混在一起。

## 7. 修改何时生效，以及怎样避免丢进度

1. 程序启动时读取 YAML。保存文件不会实时改变已经运行的 Python 进程。
2. 本项目按配置、源码和数据身份选择续训。配置变动可能创建新套件；显式恢复时，训练子任务还会读取其保存的 `active_config.yaml`。
3. 因此，“重新运行”不等于“把新 YAML 强行套在旧权重上”。不要编辑实验目录中的冻结配置或身份字段来绕过检查。
4. 已运行结果的实际配置查看 `experiments/<运行名>/active_config.yaml` 或 `resolved_config.yaml`，不要只看当前 `configs/`。
5. `progress`、`dashboard`、`open_browser` 属于显示设置，不改变数学目标；但子任务续训仍可能采用保存的显示配置，不能据此断言修改根 YAML 就会覆盖一切。
